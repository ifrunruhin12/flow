# ADR-001: Flow Streaming Gateway

- **Status:** Accepted (V1.0.0)
- **Date:** architecture revision
- **Deciders:** project owner + architecture

## Context

Flow's members must stream audio, but Navidrome must remain reachable only through the private Docker network and **no browser or future native client may ever receive Navidrome credentials or JWTs** (task A; NFR-SEC-002). The prior design (v1.0.0-draft) issued "short-lived, per-user, scoped" Navidrome Subsonic stream URLs to clients, which embeds a Navidrome JWT in the URL — a captured URL is a reusable Navidrome session for that user, and it exposes the Navidrome host. That violates the isolation goal.

Navidrome's Subsonic `stream` endpoint (verified: `server/subsonic/stream.go`) supports `timeOffset`, `format`, `maxBitRate`, and — for seekable streams — HTTP Range via `http.ServeContent` (verified: `core/stream/media_streamer.go`); transcoded (non-seekable) streams set `Accept-Ranges: none`. This is enough to proxy.

## Decision

Flow is the **only** client-facing streaming gateway:

1. Clients request audio from Flow: `GET /audio/{mediaId}` (plus `/audio/coverart/{id}` for artwork). No Navidrome URL, credential, JWT, or internal address ever reaches a client.
2. Flow **authenticates and authorizes every stream request** against the current Flow session, user status, and provisioning state before validating or disclosing media-specific request errors.
3. After validating the request, Flow atomically registers a cancelable handle under both the Flow session and user **before any Navidrome lookup or stream open**, then rechecks the authoritative session/account state. A concurrent suspension therefore either rejects registry admission or cancels the registered context.
4. Flow verifies media access with the requesting user's member-scoped `getSong`, then opens Navidrome `/rest/stream` with that same registered context and the appropriate **server-side** credential (member-scoped for a member's stream; the admin credential only for the admin's own streams). There is no administrator fallback for a member.
5. The proxy is **streaming, not buffering**: `io.Copy` pipes bytes Navidrome→Flow→client; the entire file is never held in memory.
6. The proxy forwards Range requests and upstream `206`, `Content-Range`, `Accept-Ranges`, `Content-Length`, and `Content-Type` only when supplied by the selected representation. Original/seekable streams can support byte ranges; non-seekable transcoded streams may return `Accept-Ranges: none`. Flow never promises or synthesizes byte-range support. Initial transcoded seeking uses Navidrome's verified integer `timeOffset` contract. Client abort ⇒ context-cancel of the upstream.
7. Suspended/deleted/incomplete-provisioning users cannot open a new stream; no Navidrome connection is made for a request that fails authorization, validation, registry admission, or the post-registration account recheck.
8. **Termination on revocation:** logout aborts streams opened by that session. Suspending or deleting a member blocks new registry admission, aborts all streams for that user (across sessions), and generation-evicts the user's cached Navidrome JWT. New requests are rejected after the corresponding session/user state change.
9. Navidrome internal addresses never appear in client-facing responses (logs redact them; responses carry no upstream URL).

## Alternatives considered

- **Signed per-user Navidrome stream URLs (prior design):** puts a Navidrome credential into the client's possession; a captured URL = a reusable Navidrome session; exposes the Navidrome host. Rejected on isolation grounds.
- **Let Caddy proxy `/audio` straight to Navidrome:** would hand members direct Navidrome ingress with their own credentials — the exact bypass the security model forbids. Rejected.
- **Client-side transcoding / downloading the file then playing locally:** breaks "no whole-file buffering," defeats the original-quality stream, and (for downloads) conflicts with the V1 "members cannot download" gate. Rejected.
- **A dedicated streaming proxy service (separate Go binary / sidecar):** an unnecessary microservice for a single-instance V1; the gateway is a package inside the Flow backend (`internal/streaming`). Rejected (NFR-SCALE-003).

## Consequences

- **Security:** a fully compromised member client holds *zero* Navidrome material; worst case is replaying the Flow gateway as themselves, read-only, while their Flow session lives. Suspension kills in-flight audio immediately.
- **Performance:** every audio byte transits the Flow backend ⇒ it is a bandwidth + CPU path. Mitigations: unbuffered `io.Copy`, a hard per-user admission cap, and Caddy with `flush_interval -1` and pooling (DEPLOYMENT §3). This is accepted for a private, low-concurrency platform (NFR-PERF-004); revisit only if it becomes a real bottleneck.
- **Reliability:** a Flow backend restart interrupts all in-flight audio (clients reconnect and re-request). The gateway must be crash-safe (no stuck upstreams): client aborts and context cancellation bound the lifetime of every proxied stream.
- **Representation truthfulness:** original versus transcoded behavior is tested separately against the pinned Navidrome release; Flow passes through what the upstream can actually provide rather than normalizing every response to `206`.
- **Simplicity:** one place to add stream observability, caps, and the future download variant (M10) — the download path is "the gateway, with a `Content-Disposition: attachment` variant."

## Security implications

- Credential isolation: Navidrome admin and member credentials live **only** in the Flow backend process; see SECURITY §4.
- The `enableDownloads`/`enableArtworkUpload` Navidrome gates must be off (deploy invariant) so the gateway's read-only model cannot be widened by Navidrome config (SECURITY §4 item 6, NAVIDROME_INTEGRATION §7).
