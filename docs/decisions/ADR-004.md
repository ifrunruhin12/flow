# ADR-004: Durable Membership Provisioning

- **Status:** Accepted (V1.0.0)
- **Date:** architecture revision
- **Deciders:** project owner + architecture

## Context

Approving a membership request creates state in **two systems that cannot share a transaction**: a Flow `users` row (Postgres) **and** a Navidrome user (via the native API, `POST /api/user`, admin credential). The prior design described "one transactional flow" / "same tx" for this — that is impossible across a Postgres commit and an HTTP call. A crash or Navidrome 5xx mid-flow can leave a Flow user with no Navidrome counterpart, or a Navidrome user with no Flow link.

Task D: replace cross-system atomic-transaction claims with a **durable, retry-safe provisioning state machine** that includes states, idempotent user creation, encrypted random member credentials, Navidrome user-id mapping, retry/failure handling, compensation and cleanup, and auditing — and **never lets a partially provisioned user become active**.

## Decision

Provisioning is a per-user, **persisted, idempotent state machine** (`users.provisioning_state`), driven by the `membership` service (plain Go; no HTTP handlers). Postgres is the source of truth for the state; each step is written to commit **before** or **immediately after** its side-effect so a crash resumes from the correct step.

### States (persisted in `users.provisioning_state`)

```
not_started → credential_ready → creating_nd_user → linking → complete
                    │                    │            │
                    └────────────────────┴────────────┴──► failed
```

- `complete` + `status=active` is the **only** state in which a user may log in or stream. Login and the gateway both check it (`account_not_active`). **A partially provisioned user can never become active.**
- The admin list (`GET /admin/users`) surfaces `in-flight` and `failed` states so a stuck member is visible and repairable.

### Steps (each idempotent)

1. **`credential_ready` (must commit before remote I/O)** — generate `P_m` with `crypto/rand`, encrypt it with the active external key version, and commit `navidrome_password_enc`, `navidrome_cred_key_version`, and the state transition in one PostgreSQL transaction. A crash from this point onward can always recover the exact credential.
2. **`creating_nd_user`** — call `POST /api/user {userName, password:P_m, email, isAdmin:false}` with the durable credential. On a timeout or "already exists", query by username and authenticate as that user with `P_m`. Successful authentication proves this is the recoverable account; a username collision with different credentials moves to `failed` for operator resolution. Retries never generate a replacement password.
3. **`linking`** — capture and commit `navidrome_user_id`; assign/verify the intended library set using the pinned adapter contract. The default-library behavior may be used only after the pinned release test verifies it.
4. **`complete`** — provisioning done; the user may now be `active`.

### Failure and retry

- Any step failure (Navidrome 5xx, timeout, 4xx other than "exists") sets `provisioning_state = failed` with an audit entry (`provisioning.<step>`, outcome `error`, correlation id). The state is **stable**: it does not auto-flap.
- **Retry:** admin `POST /admin/users/{id}/retry-provisioning` resumes from `provisioning_failed_step` and decrypts the already committed credential. Retrying a transient failure is safe and never changes the remote password unexpectedly.

### Compensation and cleanup

- If a crash occurs after Navidrome creates the user but before Flow records the ID, retry authenticates the matching username with the durable credential and completes the link. Flow never treats username equality alone as proof of ownership.
- **Deletion compensation:** `DELETE /admin/users/{id}?hard=true` first revokes Flow access and persists `navidrome_cleanup_state=pending`, then performs a best-effort `DELETE /api/user/{navidrome_user_id}`. Success becomes `complete`; a remote failure becomes `failed`; both transitions are audited. If a crash/timeout may have created the remote user before Flow captured its ID, cleanup resolves the username and proves ownership with the durable credential before deleting; it never deletes on username equality alone. A repeated hard delete retries pending/failed cleanup. Soft delete leaves the Navidrome user intact with `not_requested`.
- **Suspend** (no compensation needed on the Navidrome side in V1, since members have no direct Navidrome path): `status=suspended` ⇒ session rows deleted + active-stream registry flush + cached member JWT evicted.
- **Reactivate:** requires `provisioning_state = complete` (else 409) — you cannot activate a half-built user.

### Auditing

Every transition writes `audit_log` with a **correlation id** and **outcome** (`ok`/`error`/`in-progress`): `provisioning.creating_nd_user`, `provisioning.linking`, `provisioning.complete`, `provisioning.failed`, plus the approve/reject/suspend/reactivate/delete actions themselves. The trail is what makes a `failed`-state user debuggable without re-implementing the flow.

### Encrypted random member credentials

Each member gets a server-generated random Navidrome password, stored in a versioned AEAD envelope — not plaintext, not argon2 (it must be reusable server-side). PostgreSQL stores ciphertext + version only; the keyring is an external deployment secret. Rotation follows DATABASE_SCHEMA §2.12 and SECURITY §10.

## Alternatives considered

- **"One transaction" across Postgres + Navidrome (prior design):** impossible — there is no distributed transaction between a Postgres commit and an HTTP call. The claim was wrong; replaced by the state machine.
- **Saga with automatic forward-only retry and no admin surface:** would leave `failed` users unrepairable by anyone except the developer. Rejected — the admin retry/repair affordance is a V1 requirement (FR-MEM-004).
- **No durable credential (log the member in by re-issuing a password each time):** means Flow must hold the member's password anyway; storing it encrypted (not re-issuing) is simpler and auditably stable. Chosen.
- **Event-sourced provisioning (append-only log + projection):** over-engineered for one per-user flow with 3 states; a column state machine + audit log gives the same durability and is trivially queryable. Rejected (no microservices/event-bus in V1 — NFR-SCALE-003).

## Consequences

- **No partially-active users:** the `provisioning_state` gate is enforced at the auth boundary, so the worst outcome of a crash is a user who *cannot log in yet* (visible, repairable), never one who streams without a Navidrome account.
- **Retry is a feature, not a bug:** a transient Navidrome outage during approval degrades to "member not active yet, retry available," not "member broken."
- **Operational visibility:** `/admin/users` shows provisioning state; the audit log carries correlation ids end-to-end.
- **Compensation is best-effort by design:** the hard-delete of a Navidrome user can be deferred without blocking the Flow-side delete, while the persisted cleanup state keeps that work visible and retryable without an audit viewer.

## Security implications

- Member Navidrome credentials are random, encrypted, versioned, and used only server-side (member-scoped gateway calls, ADR-001) — never client-visible.
- The state machine's gate (`complete` required to be active) is a **security control**: it guarantees a streaming member always has a real, permission-scoped Navidrome principal behind them.
- Audit correlation + outcome give a compliance trail that proves who provisioned whom, when, and whether it succeeded.
