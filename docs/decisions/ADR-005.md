# ADR-005: V1 Synchronization Restart Policy

- **Status:** Accepted (V1.0.0)
- **Date:** architecture revision
- **Deciders:** project owner + architecture

## Context

The synchronized engine (task E) keeps the shared session in memory in a **single-writer executor**, with PostgreSQL checkpoints that are authoritative. Two sub-decisions needed explicit policy instead of "restore-or-end, never corrupt" (which the prior design left ambiguous between restore and end):

1. **What happens to an *active* shared session when the backend restarts (crash, deploy, OOM)?**
2. **What happens when the DJ disconnects mid-session, and how does reconnection work?**

The prior draft said "V1 may tolerate loss; auto-resume is V1.x" but did not make *safe-end* the explicit, testable V1 contract, and it did not define DJ identity/lease. Task E requires: single-instance single-writer kept; V1 shared sessions end safely after a restart; individual sessions stay persisted/restorable; mutations serialized; checkpoints authoritative; WS transient; DJ disconnect freezes position and starts a **persisted 90-second grace deadline**; reconnection verifies DJ **identity and lease generation**; grace expiry ends the session and returns everyone to Individual Mode.

## Decision

### Single-instance, single-writer (kept)

- Exactly one Flow backend instance owns the executor (NFR-SCALE-001). The executor goroutine is the **only** writer of shared-session state.
- All shared mutations (play/pause/seek/next/prev/queue/end **and** lifecycle events) are **serialized** through it.
- **PostgreSQL checkpoints are authoritative** for what has happened; the in-memory copy is the working state. The invariant is **checkpoint-before-broadcast** (see ADR-006): a crash after the checkpoint but before the broadcast is healed by a client snapshot; a crash before the checkpoint means the mutation never happened.

### V1 restart policy: active shared sessions end safely

- On boot, the executor scans `shared_sessions` for rows with `state IN ('active','paused')`. For each session, one recovery transaction marks it **`ended` with `end_reason = 'platform-restart'`**, increments `event_seq`, inserts the terminal `sync_events` row carrying the current content version, and sets `settings.mode = 'individual'`. Any later broadcast/reconnect snapshot is derived from that committed transaction.
- Reconnecting clients receive `session-ended {reason: platform-restart}` and fall back to their individual sessions.
- **Individual sessions are untouched**: `session_state` rows persist across the restart and are restorable on any device (NFR-REL-001).
- **Auto-resume of a shared session across a backend restart is a V1.x improvement (M7)**, not V1. In V1, "restart ⇒ shared session ended, everyone back to Individual Mode" is the contract. This is the deliberately simple, safe choice: it cannot resurrect a half-observed session, cannot leave two executors claiming the same session, and matches the single-instance assumption.

### DJ lifecycle: identity + active connection + server-issued fencing lease

- Every WebSocket connection receives a server-generated `connection_id`. The executor, not the client, issues a monotonically increasing `dj_lease_generation` and a random opaque lease token, stores only the token hash, and binds them to the authenticated admin user plus one `connection_id`.
- **Acquire/reconnect:** an authenticated admin connection requests the DJ lease. During grace, the new connection may acquire it; while another connection is active, acquisition requires an explicit takeover. Either path increments the generation, rotates the token, binds the new connection, and marks the old connection fenced. A client never chooses or advances its own generation.
- **Every DJ command:** must carry the current server-issued generation and opaque lease token and originate from the bound authenticated connection (WS commands) or carry generation + bound connection ID + token on the same-origin HTTP control call. The executor compares user ID, session ID, generation, connection ID, and constant-time token hash before mutation. Any mismatch is `409 stale-lease`; generation comparison alone is never sufficient.
- **Disconnect:** DJ WS close (or 3 missed lease heartbeats) ⇒ `dj_connected=false`; the session **freezes** at the current position (`state=paused`); `dj_grace_deadline = now + settings.dj_grace_period_s` is **persisted** (same checkpoint transaction) and broadcast as `dj-disconnected {graceUntil}`.
- **Reconnect within grace:** the new authenticated admin connection acquires a newly generated lease, fencing any old socket. Grace is cleared but playback remains paused until the new owner explicitly sends `play` or `end`.
- **Grace expiry:** the executor's deadline timer fires ⇒ `EndSession(reason: "grace-expiry")` ⇒ `session-ended {reason: grace-expiry}` ⇒ platform mode returns to `individual`, individual sessions restored.
- **Restart inside the grace window:** V1 ends the session immediately with `platform-restart`, just like any other active shared session. The persisted deadline is diagnostic input only; no connection or lease survives process restart.

### Transient WS

- WebSocket connections are **transient** and carry no authority: dropping all of them changes no shared state. Authority is the checkpointed Postgres row + the executor. Reconnect = re-auth (session cookie + Origin, ADR-002) + snapshot (ADR-006).

## Alternatives considered

- **Auto-resume on restart (prior draft's "offer to resume"):** requires the executor to rebuild the shared timeline across an outage and reason about which events were broadcast-but-not-acknowledged — a large surface for little V1 value, and it conflicts with the single-instance "one owner" model across a restart boundary. Deferred to V1.x (M7) where it can be designed deliberately. **Chosen: safe-end.**
- **Per-client "did I see the last event?" tracking to make resume safe:** that is effectively log-based CRDT territory; V1 has a bounded `sync_events` log for *diagnostics/replay-within-session*, not for cross-restart recovery. Rejected for V1.
- **Generation supplied by the client:** two sockets can present the same value, so it does not identify the active owner. Rejected in favor of a server-issued generation + rotated token bound to one server connection ID.
- **No persisted grace deadline (timer only in memory):** a restart mid-grace would lose the deadline and either freeze forever or restart the clock; persisting it makes the fallback total. Chosen.

## Consequences

- **Predictable restart behavior:** the only outcome of a backend restart is "shared session ended, mode individual." No partial resurrection, no split-brain (single instance), no lost individual state. This is a property you can put in a table-driven test (T6) and in the operator runbook.
- **Simpler V1 surface, clean V1.x path:** auto-resume (M7) is a contained upgrade — the checkpoints and the persisted deadline are already there; what's added is the *decision to continue* rather than end.
- **The 90 s DJ rule is now a persisted, testable deadline**, not an in-memory timer.

## Security implications

- **Zombie-DJ takeover is closed** by connection-bound token rotation and executor fencing: an old socket's token stops authorizing commands as soon as a reconnect/takeover succeeds.
- **Restart cannot privilege-escalate:** safe-end returns everyone to Individual Mode; no one gains control by the platform restarting.
- The DJ grace/fallback is a **liveness** control for the shared experience, not an auth control — it does not weaken role gating (only the DJ/admin mutates the shared session, always).
