# ADR-003: Navidrome Administrator Bootstrap

- **Status:** Accepted (V1.0.0)
- **Date:** architecture revision
- **Deciders:** project owner + architecture

## Context

Flow needs a Navidrome **admin** credential to perform admin-scoped operations (member user CRUD, scan control, config read-back, admin's own audio). The prior design assumed Flow could "create the corresponding Navidrome admin user via the native API" at boot. That is impossible for the **first** admin:

- Navidrome's native user API (`POST /api/user`) lives **inside the authenticated group** (`server/nativeapi/native_api.go`) — it requires an *existing* authenticated user. There is no "create an admin" API you can call without already having one.
- Navidrome's only first-admin affordances are **pre-auth / condition-gated**, not authenticated admin APIs:
  - `POST /auth/createAdmin` — **only allowed while zero users exist** (verified: `CountAll > 0 ⇒ 403 "Cannot create another first admin"`, `server/auth.go`), and it is rate-limited.
  - `devautocreateadminpassword` — auto-creates user `admin` **at initial setup** (verified: `server/initial_setup.go`, default empty).
- Task C: "Do not assume Flow can create the initial Navidrome administrator through an endpoint that requires existing administrator authentication. Define an operator-assisted first-run procedure."

## Decision

Bootstrap is **operator-assisted** and idempotent:

1. **Operator initializes Navidrome's first admin** using Navidrome's own supported first-run mechanism — **one of**:
   - (a) start the fresh Navidrome and use the UI first-admin creation (backed by `POST /auth/createAdmin`, valid only while zero users exist), **or**
   - (b) set the `devautocreateadminpassword` env flag in the Navidrome deploy so initial setup auto-creates user `admin`.
   The canonical production procedure is (a). Option (b) is limited to disposable development/integration environments.
2. **Operator supplies the resulting admin credentials to Flow securely:** `FLOW_NAVIDROME_ADMIN_USERNAME` / `FLOW_NAVIDROME_ADMIN_PASSWORD` in the host `.env` (`chmod 600`, never in the image, never in git).
3. **Flow authenticates and verifies the integration** at boot: `POST /auth/login`, admin user read-back (`GET /api/user/`), and pinned-release config read-back (`GET /api/config/config`). Any failure ⇒ degraded state and no product mutation.
4. **Flow stores the credential securely (implemented in M1, not M0):** ciphertext and a key-version number are stored in PostgreSQL. The corresponding master keys live only in the external root-readable keyring named by `FLOW_CREDENTIAL_KEYRING_FILE`; key material is never copied into PostgreSQL. M0 verifies credentials supplied at runtime but does not persist them.
5. **Flow establishes the admin mapping:** upserts the Flow admin row (`role=admin`, `is_navidrome_admin=true`, `provisioning_state=complete`, `status=active`) linked to the Navidrome admin user id. Idempotent — restarts just re-verify. The Flow admin's **login** password is a *distinct* Flow-side credential (`FLOW_ADMIN_PASSWORD`, argon2id); the Navidrome admin password is never reused for Flow login and never exposed to clients.

Note: with the **gateway** model (ADR-001), member streaming uses each member's *own* scoped credential, not the admin credential. The admin credential is used only for: provisioning (user CRUD), scans, the admin's own audio, config read-back, and (V1.x) metadata/maintenance.

## Alternatives considered

- **Flow creates the first Navidrome admin at boot via the native API:** impossible — the native user API requires an existing authenticated admin (verified `rx(r,"/user")` is inside the `Authenticator` group). This is the exact assumption the task forbids. Rejected.
- **Flow writes directly into Navidrome's SQLite to insert an admin row:** violates the "unmodified Navidrome, two-DB separation" invariant; a second writer to Navidrome's schema is a corruption/footgun. Rejected.
- **Navidrome external-auth (reverse-proxy) mode, with Flow the trusted proxy:** would make *every* Flow member a Navidrome principal, enlarging the trust surface; the credential-isolation model (ADR-001) keeps members' Navidrome access scoped server-side. Rejected for V1 (NAVIDROME_INTEGRATION §8).
- **Shared secret between operator and Navidrome, no env:** less explicit than an operator-supplied credential; the env-var handoff is the auditable, re-runnable step. Chosen.

## Consequences

- **A one-time, documented operator step** exists before the first usable Flow admin (DEPLOYMENT §4). The cost is a 5-line procedure; the benefit is no impossible/chicken-and-egg automation.
- **Degraded state is a defined, safe mode:** if the hand-off is wrong, Flow does not guess, does not mutate data, and tells the operator exactly what is missing.
- **Idempotent and re-runnable:** re-running bootstrap after a credential rotation just re-verifies; external key versions and database metadata support re-encryption without co-locating key and ciphertext.
- **Pinned-release evidence remains mandatory:** M0 executes the UI/createAdmin, login, and gate-readback contracts against release `v0.64.2`; source inspection alone is not labeled runtime verification.

## Security implications

- The Navidrome admin credential and the external credential keyring are sensitive host secrets. They are supplied through root-readable environment/secret mounts, never committed, and never reach a client. Backups require the database dump and a separately protected copy of the matching external keyring.
- Because Flow does **not** create the first admin, there is no API path where a pre-authenticated request becomes an admin — the first admin is always an explicit, operator-performed Navidrome first-run act.
- The degraded-state check (config gates read-back) prevents a silent security posture regression (e.g., someone flips `ND_ENABLEDOWNLOADS=true`).
