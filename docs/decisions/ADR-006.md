# ADR-006: Synchronization Event Ordering

- **Status:** Accepted (V1.0.0)
- **Date:** architecture revision
- **Deciders:** project owner + architecture

## Context

The synchronized protocol (task E) needs precise, unambiguous ordering guarantees so that many clients, over a lossy WebSocket, converge on the same shared state. The prior design conflated two things under the single name "version":

- a counter for **shared content mutations** (play/pause/seek/next/prev/queue), and
- a counter for **all** state events, which also includes **lifecycle events that do not change content** (`dj-disconnected`, `dj-reconnected`, `session-ended`). Session creation is represented by one composite `session-started` event that includes the mode transition and full state.

If one counter is used for both, clients cannot answer "is this event newer than my last snapshot?" in a way that distinguishes *content* from *lifecycle facts*, and gap/staleness reasoning breaks (e.g., a `dj-disconnected` carries no new content, so a content-only version can't order it). Task E asks for the distinction to be made explicit, with snapshot consistency, stale-event rejection, **sequence-gap detection**, and resynchronization behavior.

## Decision

Two counters, deliberately separate, per active shared session:

### 1. `version` — order of shared **content**

- Bumped **only** on content mutations: `play`, `pause`, `seek`, `next`, `prev`, `queue` (and session create, `version=0`).
- Lets a client ask "is this event's payload content newer than the content I have?"

### 2. `event_seq` — order of **all** authoritative state events

- Bumped on **every** authoritative state event, including lifecycle events that leave `version` unchanged (`dj-disconnected`, `dj-reconnected`, `session-ended`).
- Always strictly increasing per session; **the WS envelope `seq` field is exactly `event_seq`.**

### Invariant: one authoritative state event per `event_seq`

- **Exactly one row is written to `sync_events` per `event_seq` value** (UNIQUE `(shared_session_id, event_seq)`), and that insert is committed **in the same Postgres transaction as the `shared_sessions` checkpoint**, *before* the WS broadcast (the checkpoint-before-broadcast invariant, ADR-005).
- Consequence: **a WS frame whose `event_seq` has not committed to Postgres can never be observed** (no phantom events on crash), and the persisted log is total-ordered per session.

### Snapshot consistency

- Reconnect uses the WebSocket **subscribe-before-snapshot** protocol, not a separate `GET` followed by an unrelated subscription. Under the hub's subscription lock the server registers the connection and begins buffering authoritative events; it then reads the committed checkpoint `(version, event_seq, refTs, queue, state, …)`, sends that snapshot, drains buffered events with `event_seq > snapshot.event_seq` in order, and finally switches the connection to live delivery.
- Events committed between subscription and snapshot are either reflected in the snapshot or present in the buffer; events committed after the snapshot are buffered. Therefore sequence N+1 cannot fall into the snapshot/subscription gap. Buffer overflow or a detected gap forces a new subscription cycle.
- `GET /sync/state` remains useful for diagnostics and HTTP clients, but it is not by itself a reconnect-consistency protocol.

### Stale-event rejection

- After taking a snapshot at `(version V, event_seq S)`, a client drops frames with `event_seq <= S` and applies frames with `event_seq > S` in strict order.
- Staleness is judged by `event_seq` (not `version`) — this is precisely why the two counters exist: a lifecycle event can carry the *same* `version` as the prior content state yet must still be ordered.

### Sequence-gap detection and resynchronization

- On a **live** connection, if a client observes `event_seq` **jumping** (it receives seq N+2 before N+1), that means a frame was lost on that connection ⇒ the client **immediately takes a fresh snapshot** (resync source), then resumes applying in order.
- Because events are **not** retransmitted on a single connection (loss = reconnect + snapshot), a gap on a live connection is treated as "the connection is not a reliable transport" ⇒ snapshot.
- After any resync, the **drift-correction loop self-heals content**: a missed content mutation surfaces as position drift and is corrected within one heartbeat cycle. So even a dropped `sync-next` is recovered without a dedicated retransmission path.

### Event semantics

- Every authoritative event carries the **current** content `version`, including lifecycle events whose version did not change.
- One executor command/transaction produces one authoritative event. If it changes several logical fields (for example next-track changes queue index, media ID, position, and reference timestamp), the event is a single composite `state-changed` payload.
- Starting a shared session commits exactly one composite `session-started` event at `version=0,event_seq=1`; ending it commits exactly one `session-ended` event that includes the resulting platform mode. A separate authoritative `mode-changed` event is not emitted for the same transaction.
- Per-client corrections, heartbeat acknowledgements, and `hello` are transient messages. They do not increment `event_seq` and use `basedOnEventSeq` when they need to identify the authoritative state they were computed from.

### Summary of the contract

| Concept | Counter / rule |
|---|---|
| Content ordering | `version` (bumped on content mutations only) |
| Total event ordering | `event_seq` (bumped on every authoritative event; = WS `seq`) |
| Exactly-one-per-seq | `sync_events` UNIQUE(session, event_seq); checkpoint + insert in one tx, before broadcast |
| Snapshot | atomic subscribe → committed snapshot → buffered drain → live |
| Stale rejection | drop `event_seq <= snapshot.event_seq`; apply `>` in strict order |
| Gap ⇒ resync | any observed `event_seq` skip ⇒ fresh snapshot; drift loop heals content |
| Not a replay log | `sync_events` bounded (500/session), diagnostic — not cross-restart recovery (ADR-005) |

## Alternatives considered

- **Single counter for everything (prior design):** cannot distinguish "same content, new lifecycle fact" from "new content"; gap/stale reasoning breaks for `dj-disconnected`/`session-ended`. Rejected — replaced by two counters.
- **Contention-free sequence via Lamport clocks / hybrid logical clocks:** over-engineered for a single-writer, single-instance system; a plain monotonic per-session counter under the single-writer executor is total-order by construction. Rejected.
- **Per-event acknowledgment + retransmission (reliable-WS):** adds a second reliability layer the drift loop already provides for content; V1 keeps "loss ⇒ snapshot" as the single, testable rule. Rejected for V1.
- **Log-structured replay across restart:** would make `sync_events` a crash-recovery mechanism, entangling it with the restart policy. ADR-005 keeps restart = safe-end, so the log stays a bounded diagnostic artifact. Chosen.

## Consequences

- **Deterministic convergence:** every client's state is a function of `(snapshot, applied events by event_seq)`; the two-counter split makes "stale?" and "new content?" separate, decidable questions.
- **Crash-safe by construction:** checkpoint-before-broadcast + one-event-per-seq means a crash can never produce a broadcast with no committed backing (no phantom), and a snapshot always matches the last committed checkpoint.
- **Testable:** the invariants are table-driven tests (fake clock): exactly-one-per-seq, checkpoint ordering, stale rejection, gap⇒snapshot, and the zombie-DJ generation check (ADR-005) composes cleanly.

## Security implications

- **No lost-update on authority:** because the executor is the single writer and events are total-ordered and checkpointed, two clients can never commit the same `event_seq` or apply a stale one — the shared session is a single-writer log the clients only read (and report into).
- **Resync is idempotent and cheap:** a snapshot is a read of the committed checkpoint; a malicious client cannot advance or skip the shared timeline by injecting events (only the DJ/admin, through the executor, mutates it).
- **Gap detection bounds an attack surface:** a client that drops/reorders frames is forced back to the authoritative snapshot rather than being able to "pin" a stale state.
