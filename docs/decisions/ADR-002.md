# ADR-002: Browser Authentication and Sessions

- **Status:** Accepted (V1.0.0)
- **Date:** architecture revision
- **Deciders:** project owner + architecture

## Context

V1 is **browser-only** (Android/desktop land later with the same API contract). The prior design used signed JWTs "plus a server-side revocation list" — a hybrid that is stateless *in name* but actually requires the revocation list to be consulted per request, so it never gains the statelessness it claims, and it still ships a signed token to the client. Task B asks for **opaque server-side sessions** for the browser, with immediate server-side revocation, CSRF protection, and WebSocket Origin validation, and **no credentials or session tokens in WebSocket query parameters**.

## Decision

For the browser (V1), Flow uses **opaque server-side sessions**:

1. **Token:** on login, Flow generates a **cryptographically random 32-byte token** (`crypto/rand`). The client receives it in an **HttpOnly, Secure, `SameSite=Lax`, `Path=/`** cookie (`flow_session`). The token is opaque — it carries no claims, is not signed, and is not decodable.
2. **Storage:** only the **SHA-256 hash** of the token is stored in PostgreSQL (`sessions.token_hash`), with `user_id`, `expires_at` (default 8 h, FR-AUTH-004), and `last_seen_at`. The raw token never touches the DB (a leak of the DB does not leak usable tokens).
3. **Validation:** every request (REST and the WS upgrade) resolves the cookie → hash → `sessions` row → user. If the row is missing (expired, logged-out, suspended) ⇒ `401`. This is a per-request DB lookup; at V1 concurrency that is acceptable and it is exactly what makes revocation immediate.
4. **Account status enforced during authentication:** a valid session still checks `users.status` and `provisioning_state` on every request (`account_not_active` ⇒ 403). Suspension deletes the user's session rows and synchronously asks the gateway registry to abort all stream handles for that user (ADR-001).
5. **Logout / revocation:** `POST /auth/logout` deletes the session row and synchronously flushes stream handles bound to that session before returning. No "grace period," no in-memory revocation set to drift out of sync with the DB.
6. **CSRF protection:**
   - `SameSite=Lax` blocks cross-site cookie submission for `POST/PUT/PATCH/DELETE` (attached only to top-level GET navigation, which in this API is read-only).
   - Defense-in-depth: the backend validates the **`Origin` (or `Referer`) header** on cookie-authenticated mutations; mismatch ⇒ 403. No double-submit token in V1 (documented, tested control — SECURITY §5, acceptance test 3).
7. **WebSocket authentication:** the `Upgrade` on `/ws` authenticates with the **same session cookie** (validated server-side) **plus an `Origin` equality check** against the configured domain. **No token in the query string, no `Authorization`-header JWT, no separate WS token** (task B explicit). `401` (no/invalid session) or `403` (origin mismatch).
8. **Future native clients:** a **separately defined bearer-session mechanism** — the same opaque-token model (random token, hashed at rest, immediately revocable), but issued on a native login endpoint and presented via `Authorization: Bearer`, with the Origin check relaxed (no cookie). Reserved, not implemented in V1 (FR-AUTH-008, `POST /auth/native/login` returns 501).
9. **First-login restriction:** member approval/direct creation/reset uses an admin-supplied temporary Flow password communicated out-of-band. A successful login may create a session with `must_change_password=true`, but middleware restricts it to `/auth/me`, `/auth/change-password`, and logout. Changing the password clears the flag, preserves the current session, and revokes all other sessions.

## Alternatives considered

- **Stateless signed JWTs (no DB):** cannot revoke without a side-channel list; a "revocation list + JWT" is strictly worse than a session table (you keep the JWT plus the table). For a browser product where immediate suspension must stop *audio*, the DB session wins.
- **JWT-only with a short TTL (e.g., 15 min) and no revocation:** suspension stops working within TTL, not immediately — unacceptable for a security control. Rejected.
- **Opaque token kept in `localStorage` + `Authorization` header:** storable/leakable by XSS; the HttpOnly cookie + SameSite model is the safer default for a browser SPA. Rejected.
- **A per-request DB lookup is "too slow":** at V1's private-platform concurrency (dozens of users, audio is proxied not polled), one indexed PK lookup per request is negligible. Accepted.

## Consequences

- **Immediate, authoritative revocation:** logout, suspension, and delete remove authoritative session rows; REST/WS fail their next validation, while the lifecycle service synchronously flushes the applicable gateway handles for in-flight audio.
- **One source of truth for "who is logged in":** the `sessions` table. No split-brain between a token and a revocation list.
- **DB coupling:** authentication now depends on Postgres availability (a DB outage ⇒ no new requests). Acceptable: the whole platform is down without the DB anyway.
- **Native clients (V1.x+):** the bearer mechanism is a new, small surface (`client_sessions`), not a rewrite — same token/hash/revocation model, different transport.

## Security implications

- Token theft is bounded: an attacker with the cookie can act as that user until logout/suspension (row delete) — same as any session cookie; mitigated by `Secure` + `SameSite=Lax` + HttpOnly.
- WS cross-origin attacks are closed by the Origin equality check (a foreign page cannot open a WS to `/ws` with the victim's cookie and a different `Origin` — the server rejects the upgrade).
- No long-lived signed material exists to leak from the DB; the DB holds hashes.
